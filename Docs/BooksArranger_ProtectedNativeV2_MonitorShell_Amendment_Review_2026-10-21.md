## Deadline coordination: accepted finite direction

One TryAcquireSRWLockShared attempt removes the worker-held blocking Acquire dependency. If it fails, the monitor must read no Job field/handle and immediately request termination of its own watcher through GetCurrentProcess. This cannot target a foreign numeric PID/Job and relies on the already-created noninherited private KILL_ON_JOB_CLOSE handle. No retry, wait, spin, sleep, host IO, close attempt or deadline extension may precede that false-try fatal path.

If the try succeeds, only the original still-protected Job handle may be inspected/terminated and the lock must be released before the unconditional self-termination path. It must not perform member enumeration, hashing, close/join/wait or worker callback while holding the lock. Any failed Job termination still proceeds to self-termination; no exception or diagnostic output may prevent it. Unexpected return from attempted self-termination must never resume normal work or produce a successful frame/closure assertion. The existing failed flag, normal frame-before-monitor-teardown ordering and original deadline remain unchanged.

This resolves a worker-coordination dependency by design; it does not prove every trusted Windows kernel API is interruptible or supply emergency checked-closure evidence. Emergency self-termination/private Job close remains failure/UNKNOWN scope, not successful retained/member/input/Job close. Normal success still requires all checked work closes, real EOF, frame write, checked monitor/control teardown and actual original tool termination within its original bound.
