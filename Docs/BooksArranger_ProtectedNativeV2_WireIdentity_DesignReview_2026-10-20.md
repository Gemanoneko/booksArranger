## Accepted choices and mandatory interpretation

The byte graph is acyclic: existing immutable context/manifests and guardian plan precede runtime sidecar/policy, policy precedes registry, and the actual registry digest is externally pinned. No policy self/registry digest or reconstructed-JSON digest is permitted. Keep the existing 93-member bootstrap allowlist, which excludes the registry, policy and bootstrap manifest itself; the external install inventory cannot be made self-hashing. Mandatory raw guardian-plan and actual held Node hashes in the terminal close the previously identified digest omissions.

All 17 registry keys, exact policy/ref shape, guardian context ref, context source manifest, exact decoded runtime-sidecar data and actual held paths/bytes must join independently at PRE, native producer, fixed launcher and POST. Node is the fixed admitted executable and agrees with the guardian/context runtime, not merely another same-hash pathname. Source snapshot/harness/runtime exact closure and mapped repository complete:false semantics remain distinct. The unchanged canonical child retains its existing Git checks; native prechild proof does not attest future Git state.

The selected raw payload cap 12,574,720 encodes to 16,766,296 base64 bytes. This leaves 10,920 bytes below the 16,777,216 outer cap for terminal and all literal headers/newlines; the 8,192-byte terminal ceiling fits. Both writer and parser must still compute the complete actual wire size with checked arithmetic before allocation/write, including empty payload and decimal-width boundaries. Base64 is one canonical padded line; decoded child output is opaque. No marker search, secondary frame or nonempty outer stderr is accepted.

Strict decoding includes duplicate keys after JSON unescaping at every level, unknown keys, invalid UTF8 and unpaired escaped surrogates, decoded NUL/path escapes, and checked integer/nesting/token/string/array/ref quotas. The literal fixed-order terminal must reserialize byte-identically; neither ordinary JSON.parse nor a trusted-looking shape alone supplies this property. Counts and size additions are checked before size_t/DWORD narrowing. Large files are streamed; native parsing must not turn the 1GiB file ceiling into an allocation request.

Full native file/directory identity, ordinary/default-stream/link/ancestry proofs, protected owner/DACL checks where required and held-byte hashes must precede release and remain retained through closure. No existing legacy-ID reader or JS validation is silently promoted into the new full-identity contract. Initial creation-returned handles, exact Job assignment and identity/image checks precede release. Newly sampled objects need admission proof; continuously retained objects use their actual held identity/wait/Job observations and image-at-admission provenance. These are requirements for NEW native code, not engineering-owned-object-v3 equivalence.

The selected two-pass reconciliation retains the original and separately registered candidate obligations, records the initial diagnostic before new native calls, requires actual same-object comparison and checked duplicate close, then discards the entire stale pass once. Different/unknown/failed-close observations remain failure; no PID absence, live-image retry or partial sample can become authority. All passes and diagnostic work consume the same original budget. Unknown/non-Job candidates grant no out-of-Job termination authority.

## Two advisory specification Minors

1. **retained_closed needs one exact counting definition.** Define it as the count of successfully closed distinct admitted process-object obligations, including the initial child and every obligation retained from discarded passes. Creation/thread/pipe/input/Job handles and a same-object diagnostic duplicate are separately checked closes, not extra process obligations. A different/unknown failure-only candidate cannot disappear from accounting or yield a success frame. max_members applies over retained lifetime, not only one live sample. Add these exact boundary cases; no new success schema is needed.

2. **Unique-object quotas do not alone cap duplicate handles.** Repeated identical refs may not allocate a fresh retained handle on every reference while incrementing max_objects only once. Reuse the held identity/ref, or immediately checked-close the redundant handle before retaining another obligation. Keep no unbounded duplicate-handle ledger. Count distinct canonical paths/identities and unique byte totals as specified; aliases/conflicting digest refs refuse. This is finite storage/cleanup accounting inside the existing input owner, not another ownership framework.
