## Documented basis and limits

Microsoft documents that termination signals the process object and that another process’s open handle keeps the object valid. This supports retaining the SAME object after exit; it does not justify obtaining a replacement handle from a reused numeric PID. [Process termination](https://learn.microsoft.com/en-us/windows/win32/procthread/terminating-a-process).

A zero-time wait returns actual current state; WAIT_OBJECT_0 is signaled, WAIT_TIMEOUT is nonsignaled, and WAIT_FAILED is failure. SYNCHRONIZE is required and closing a waited handle concurrently is undefined. The source contract must therefore preserve exclusive lexical close ownership. [WaitForSingleObject](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-waitforsingleobject).

GetProcessId and GetProcessTimes address the process selected by a handle; query-limited access suffices. The latter returns creation FILETIME with64bit precision. Successful queries on the continuously retained terminal handle provide the proposed fresh PID/creation check; failure remains unsupported. PID alone is not authority. [GetProcessId](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocessid), [GetProcessTimes](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocesstimes).

The saved2f4c records prove image-query error31 and matching reported creation fields, but contain no actual signaled wait for those failed queries. They remain closedfalse/native:null. Error31, elapsed timeout, tool exit and empty close_errors cannot supply the missing proof. No cause or retrospective native closure is inferred.
