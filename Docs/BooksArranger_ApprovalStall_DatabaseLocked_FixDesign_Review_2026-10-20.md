## Progress boundary

Use existing `inventory.group_lock` → `_progress_lock` → SQLite order. Control callers already hold group_lock before status/progress; taking the inverse order creates a real deadlock risk. RLock reentrancy is deliberate. No job/status callback or later group-lock reacquisition may occur under a progress-only filesystem phase. Release locks safely on every exception.

Check current roots/groups in a short read transaction. If stale, rollback/CLOSE before bounded fresh BEGIN IMMEDIATE retry; recheck/sync stale roots only. Current roots must not reserve a writer on every poll. Then materialize the approved-candidate/context/retired/location/retry data in one coherent read snapshot and COMMIT/CLOSE before cover/output stat, NAS access or external callbacks. Display counts are observed catalog facts, not source/publication or queue authority; external file status can change after snapshot closure.

Freeze exact replacement relation/structural proof, publication lookup and retry-intent proof under that same caller snapshot. Existing replacement `structural_guard(...,db=...)`, display-only publication lookup and retained-retry validation support DB-only checking. Do not fetch a newer relation/proof from another connection during the filesystem phase or weaken the original guard into an invented JSON boolean. Existing cache signatures must include their actual changing dependencies or invalidate on relevant catalog changes; an approved-cache entry cannot restore a stale proof or approval. Preserve original guard semantics and expose coherent acknowledged/stale facts honestly.

## Scanner replay boundary

Only DB-only task/counter/outcome/persistence transitions may retry. Current _directory commits per entry and _file executes metadata/source IO: neither entire function may be replayed on BUSY. Capture source observations once, validate before/after identity, then retry only the resulting explicitly replay-safe SQL operation on fresh connections after rollback. No FFmpeg, source hashing/reread, directory iteration, research/provider call, approval, cleanup or publication in a retry callback.

Each callback must compare the expected root/generation/task state and relevant original file/review/retirement facts before committing captured results. A concurrent review, retirement, task or source-preservation change must produce a typed catalog hold/pending outcome, **not** fall into the existing generic ValueError→media-error/review-clear branch. File/counter/outcome/done updates need one atomic result so COMMIT failure/another attempt cannot double-count. Directory insert/outcome replay must remain idempotent across its already committed prefix. An obsolete worker's failure bookkeeping must also be generation-bound; it cannot overwrite a newer job state.

Keep the existing stop/root leases and zero-error reconciliation ordering. Reacquire completion that performs native/source checks is not DB-only and must not be replayed through the generic helper; retain its existing held-proof/CAS contract and surface blocked completion when necessary. No partial/error scan may mark missing originals or completed discovery, authorize archival, reset generation or silently restart research.

Use the existing bounded helper: primary SQLite BUSY-code family only, at most30seconds/60attempts with short per-connection wait, stop-aware delay, rollback/CLOSE and fresh transaction each attempt. SQLITE_LOCKED/unknown codes and unrelated IO errors are not blindly retried or classified by English strings. If permanent contention exhausts a task or failure-save bound, preserve pending/source evidence and actual visible contention; if durable save failed, keep that uncertainty explicit instead of claiming saved failure/completion. Existing outer operation budget, when applicable to later testing, includes retries/cleanup; never reset600000ms per retry.
