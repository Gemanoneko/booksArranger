## Re-measure on the same build after a long wait (run 4, added after Jane's request)

Same installer, same copy, relaunched 20:22 UTC (private port 5213 again), read-only Z:, no mutating clicks; the harness only waited and polled for 28 minutes, then ran 3 filter changes to "Output needs attention" and back, logging every `/api/state` and `/api/inventory` call the page made (start offset, status, duration). The first list painted 65.2 s after launch (run 3: 62.9 s).

**The engine never settled.** I sampled every 20 s (84 samples). The app's 7-process tree read **1.6 to 6.8 GB per 20 s, median 5.4 GB, in every sample** (505.7 GB read and 9.8 GB written over about 31 minutes), the "converted" count stayed at **89** the whole time, and the page's own `/api/state` polls returned non-200 (503) **35 times in 134**, with per-sample median durations of 2.3 to 5.8 s. So the "Z: reads idle, Ready count stable" state never came; I stopped at my 28-minute cap and measured anyway. I did not split the reads by drive, process or file, so I cannot say how much was `Z:` and how much the local catalog copy. The local data folder is 1,103 MB (catalog file unchanged at 495,427,584 bytes), so the writes did not pile up there; I cannot prove none went to `Z:`.

**What the calls show.**
- The page asks `/api/state` first and `/api/inventory` second, one after the other. **The loading text appears at the moment the inventory call starts**, so its delay equals the state time: 1.8 s, 11.0 s (a 503 after 4.0 s, then the next state call only started at 7.3 s and took 3.7 s), 2.5 s. This matches the code reading in Finding 1.
- `/api/state` takes **2.3 to 4.0 s** per call and hits a **4.0 s 503 cap** on the first call in 3 of the 6 cycle windows and in about a quarter of all polls (35 of 134). The recipe expects about 1 to 2 s.
- `/api/inventory` for "Output needs attention" (100 rows) takes **1.7 to 2.3 s**; for "Audiobook Ready" (89 rows, the list the window opens on and re-polls every cycle) it takes **7.3 to 9.1 s**. That second call is the biggest single cost in the "back" direction and in the idle polling loop.
- I did not instrument the engine, so I cannot name what inside those two endpoints spends the time. The continuous multi-GB read counter next to a stuck Ready count is consistent with the Ready list re-reading finished books on every call, but that is an inference, not something I observed. Ender: profile `/api/inventory?...status=converted` and `/api/state` on this copy.
- Group-button timing was not re-measured in run 4 (my wait condition finished at once on the already-shown list); the run 3 value (loading text 15.3 s, rows 17.3 s for "Can retry") stands.

## Findings

Cause visible in the code, not proven by me as the whole story: `refresh(true)` in `web/app.js` awaits `/api/state` and only then calls `showListLoading()`; a 503 from `/api/state` throws and the click's refresh ends with a message instead of a list, so the next poll tick has to do it. Judy: the old list stays on screen for 7 to 15 s after the click with no sign anything happened. Ender: show the loading state before waiting for state; look at why `/api/state` needs 4 s and answers 503. Repro: launch the packaged app on a copy of the real catalog with the real Audiobooks root, wait for the first list, set Status to "Output needs attention", click "Can retry".
2. **Major, new, one build only (watch item). First list after launch takes about a minute** on the real Audiobooks root (62.9 s, 48.5 s, 50 s+). Earlier QA used private empty roots, so I have no earlier measurement to compare with. Cause unknown; see "What the NO-GO does not tell you".
3. **Informational. A book changes group after launch.** In every launch the first reads showed Can repair 1 and M4B not supported 2; about a minute or two later Can repair 2 and M4B not supported 1 (the total stays 131; `/api/state` late reads `retry 128, repair 2, other 0, unsupported 1`). 5. **Informational. The first Can retry row, "The Lost Symbol", says "Stopped — not enough disk space / Free up disk space, then retry."** C: has 53 GB free here. Probably a stored cause from an earlier run; Retry would re-check. Not investigated.
