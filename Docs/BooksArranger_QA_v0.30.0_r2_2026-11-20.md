## 5. Findings

### Blocker

**R2-1 (item 1, a side effect of F1). The held ancestry cleanup is re-checked at launch with no Start, and a saved user Pause does not stop it.**
- Repro (slice B, reproduced in 4 fresh fixtures; script deleted with its folder):
  1. Replay both storage moves; seed a Brom-like held row (3 originals + 3 copies, state needs_attention, "Persisted recovery ancestry changed") as 0.29.0's `hold()` writes it.
  2. Start the real engine and press NOTHING. At load `_start_generation` 0, `_automatic_cleanup_generation` 0, `_pause_depth` 0. Within 0.5 s the row is `checking`, then `completed`; originals removed (the 8-book main run: 37 originals and 37 copies at load, 0 and 0 thirty seconds later).
  3. Saved-Pause variant: press Pause audiobook jobs over the page's route (200, state Paused, `pause_attribution.jobs` = user / `restart-intent-v1`), seed the held row, Quit through the real desktop route (202, exiting after 0.3 s, shutdown trigger "quit" saved), relaunch on the same catalog, press nothing. The row ran within 0.5 s and completed (0 of 3 originals, copies purged), and the relaunched engine reported jobs state Running, then Completed, never Paused.
  4. Control, same run, no held row: the relaunched engine reports Paused and the ordinary paused cleanup stays put for 30 s, hashes equal. So the saved Pause is honoured everywhere except this sweep. Paused and waiting cleanups never started by themselves; only held rows do.
- Expected: the Brief row says "once per admitted Start … nothing starts it by itself"; the engine's own comment says "a periodic wake never does". A user Pause must hold.
- Cause, checked by me in the pinned source: `start_retention` passes `_automatic_cleanup_generation` (default 0) to `_finish_held_cleanups`; its `allow()` is true on a fresh engine because `_start_allowed(0)` tests only generation equality, not draining, not closing and the in-memory `_pause_depth`, which is raised only by an in-session Pause (`merge_service.py` 1049) and is 0 after every launch; the saved Pause (`pause_state.jobs_active`) is read at 1131 on a start path and never on this sweep. `RECHECKED_HOLDS` now includes `ANCESTRY_HOLD` (1638), so it runs.
- Severity: Blocker under the coordinator's ruling ("nothing may override a user Pause"). The outcome is the wanted one and nothing is lost (output verified first, removals only after the checks, recovery copies purged per `HOURS=0`), but originals are removed at launch although Sergei paused jobs and pressed no Start.
- Not established: whether 5dbba45's older `HELD_FOR_METADATA` holds already launch-sweep past a saved Pause (same code path, not run on the baseline); a separate-process run (slice B's engines shared one process).
