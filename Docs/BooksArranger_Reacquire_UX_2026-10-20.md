## Classification and navigation

**Need to reacquire** is for a specifically analyzed source whose audio is materially damaged, or whose decode failure cannot be established safe to repair without losing meaningful audio. It is not a catch-all for attention, unsupported containers, absent metadata, unavailable drives, missing files, producer holds or destination review. A decoder error alone without the bounded analysis is not proof of missing speech. Cases still being analyzed retain the actual Checking/Other state; unknown API data does not invent a reacquire decision.

If independent analysis proves harmless container damage, or a small damaged region is verified to contain only silence and the supported repair preserves meaningful audio, use the existing **Can repair → Repair** flow. Do not silently treat a few seconds as harmless, invent a duration threshold or copy silence over uncertain speech. When a container can be preserved and validated unchanged, use the existing Retry path rather than calling it corrupted audio. Final repair/Retry success still requires ordinary checks and does not certify completeness from a folder scan.

Within **View: Book candidates → Status: Output needs attention**, extend the existing wrapping Reason strip with one quiet button **Need to reacquire · N**, immediately after Can repair. Tooltip **Show books whose damaged audio needs a replacement source.** Accessible group and aria-pressed behavior match the existing reason buttons. No second category page, new settings or deletion/marking control. The category appears for a nonzero authoritative count, or while selected/focused when zero, following the existing empty-group transition. Counts and filtering are server-side, distinct by current candidate identity before pagination. Each candidate belongs to one primary attention group; a reacquire candidate is not also added to Can retry/Can repair. Output-issue totals include it exactly once. Source availability is a separate secondary fact, not another counted group. Unknown counts read unavailable rather than guessed zero.

## Manual deletion and fresh replacement

This follows Sergei's authorized workflow: he removes the damaged originals himself and places an intact replacement in an unsorted source. There is no Delete files button, confirmation dialog or automatic damaged-source deletion. **Start scanning** is the existing action for observing filesystem changes; **Start automatic processing** is the existing action for discovery plus fresh research. Scanning alone does not promise research or conversion.

Only an explicitly reacquire-marked candidate is eligible for clearing its active source/catalog entry after **all original source members** are confirmed absent through a completed, successful check of accessible source roots and containing directories, with normal identity/concurrency checks. Unreachable/offline/denied root, interrupted scan, incomplete enumeration or an access error is not deletion. Show **Source unavailable — deletion not confirmed** with actual path/reason and **Connect the source drive and scan again.** Use an access-specific instruction when connectivity is not the failure. Keep the active entry and reacquire decision; never count inaccessible members as deleted.

If some members remain, show **Some original files remain** and **The book stays listed until all its original source files are confirmed gone.** Keep the remaining affected paths inspectable. Do not clear other candidates or unrelated files from a shared collection. Ender must account for grouping/shared-source dependencies and publication/recovery references before clearing active entries; history/receipts required by those references stay retained. A dependency that prevents reconciliation gets its actual reason rather than a false cleared result. This spec does not authorize erasing historical jobs, receipts or recovery evidence.

When completed accessible reconciliation confirms the marked originals are all gone, remove that old book from active candidate/attention listings and update totals from the same acknowledged catalog snapshot. If its details are selected, keep a normal-flow notice **Damaged originals confirmed removed. Scan the replacement for fresh research.** with no active conversion controls; move focus only if its focused control is removed, using the existing details-heading/status pattern. The notice is not another persistent candidate or attention count.

A replacement discovered at the same path/name is still new source content. It must get fresh identity/research/recording/order/output eligibility checks; do not carry the old damage verdict, source approval, source hashes, queue intent or candidate approval onto it. Manual-source evidence/history may remain recoverable but cannot auto-apply stale acceptance to the new recording. If a replacement arrives before a deletion-only scan, reconcile the changed source safely and research the replacement afresh rather than requiring the user to recreate the deletion sequence. A title match, reused filename or scan discovery is not proof of sound audio or a complete book. No automatic queue solely because an old damaged entry disappeared.

## Held work is not Converting

Current activity kind alone must not select **Converting** for a nonrunning row. Resolve visible activity heading from acknowledged state first: running conversion **Converting**, pausing **Pausing audiobook**, paused **Audiobook paused**, attention **Audiobook on hold**. For an analyzed reacquire hold the next line is **Need to reacquire — {short analyzed reason}**; other holds retain their actual existing readable reason. If no worker/activity is active and zero books are queued, do not retain a stale running conversion row or animated bar. Use existing **Nothing running** when there is no current activity; if a genuine hold is displayed, show its held row without progress animation, ETA, advancing elapsed time or a promise to resume. Zero queue alone does not prove no running work: a real current worker may be processing the last book. Backend activity identity/state remains authoritative.

No per-poll announcements or focus movement. Announce a meaningful newly acknowledged classification/deletion result politely once. Disconnected data stays marked Last confirmed; a failed poll cannot certify deletion, completion or worker stop.
