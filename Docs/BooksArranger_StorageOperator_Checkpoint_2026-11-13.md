## Source consent and SQLite

`prepare_source(..., apply=False)` returns an explicit complete plan with `catalog_id`, `generation` and `consent_sha256`. Applying requires the same IDs and `expected_plan_sha256=preview['consent_sha256']`. A raw hash of the whole returned JSON is not the consent hash. Fresh native ownership, membership, full hashes, security descriptors and schema/history are checked again before the first source-fence mutation.

All SQLite inspection and the APPLY consistent backup finish **before** the final retained source census. SQLite read-only WAL inspection can update the exact main catalog SHM file's LastWriteTime; therefore the consent projection normalizes **only that SHM modified field**. It still binds SHM identity/size/full bytes, all main DB/WAL facts and content, all other file facts, DACLs, source/target roots and states. The saved source plan has a separate byte SHA and retains the actual fresh SHM native facts. The private WAL case verifies exact fresh facts/hash and the committed WAL value in the backup. No claim of zero SQLite SHM bookkeeping writes is made.

Source plan/security descriptors are saved with CREATE_NEW before DACL changes, with per-item phase evidence and a consistent SQLite backup. Source fences deny Everyone data/append/create/EA/attribute/delete rights, preserve readable bytes, and retain exact original descriptors/owner for recovery. `SetSecurityInfo` may alter the documented `SE_DACL_AUTO_INHERITED` bookkeeping bit: source restore compares exact owner/group/protection/ACE order, permissions, SIDs and inheritance flags while permitting only that bookkeeping difference. The original full descriptor bytes are retained.

For a copy preserving source security, the target's actual `.lock` owner is acquired using read/list + READ_CONTROL/WRITE_DAC and deny-WRITE/DELETE sharing. Only target ACLs are restored. Source-original effective ACLs are protected on the new volume to avoid broadening them through the I: parent's different inherited ACLs. Owner/group and ACE order/masks/SIDs/propagation flags remain checked; only the deliberate target protection and inherited bookkeeping conversion differ. Original source remains write-fenced.

The source may be renamed to a physical rollback root; sealing requires that explicit path and its original native root identity. The old C: alias naming the new I: target can never serve as proof of the original source fence. Full membership is rechecked after fencing, including app-state directory ADS, before the source-fenced result is returned.

## Public phase APIs

1. `prepare_source(source_root, target_root, scopes, catalog_relative, workspace, apply=False, ...)` — inspect by default; applied form requires the consent SHA and same IDs.
2. `seal_target(source_plan, source_plan_sha256, source_fence, source_fence_sha256, source_original, manifest_path)` — verifies an independently copied tree; the operator does not copy/move the shared folder.
3. `activate_target(manifest_path, manifest_sha256)` — **verification-only** phase/revision `verifying/2`. It does not enable normal app/library work.
4. `verify_target(manifest_path, manifest_sha256, verification_path=None)` — independently reopens original and target, verifies source facts/hashes, target directory identities, non-DB membership/bytes and original catalog schema/history. Creates NEW pinned proof, default `<manifest>.verified.json`.
5. `enable_target(manifest_path, manifest_sha256, verification_path, verification_sha256)` — fresh proof recheck then `verifying/2 → active/3` CAS and verification registration in the **same** FULL-synchronous transaction.
6. `rollback_unwritten(manifest_path, manifest_sha256)` — refuses new unreconciled decisions/work. Fences the target first, then restores the exact original source permissions. Both copies remain; no stale snapshot overwrite.
7. `recover_unactivated_source(source_plan, source_plan_sha256)` — permission recovery for interrupted source preparation **only while no selected target scope exists**. Exact source IDs and original ACLs, no content removal or rewind.
8. `verify_source_fence(path, sha256)` — context manager with `.receipt` and `.revalidate()`. Initial complete native/security/membership verification; retained deny-write handles and cheap root/admission-fence checks through the owning catalog lifetime. It does not hash 25 GB for every runtime comparison.

The activation table's eight fields match the shared core contract. Additional verification table:

```sql

  receipt_sha256 TEXT NOT NULL, verified_state_sha256 TEXT NOT NULL)
```

The verification receipt schema is `books-storage-target-verification-v1`. It includes manifest physical path/SHA, catalog/generation, source snapshot/plan/fence SHAs, verified-state SHA, original catalog logical SHA, source-original/target roots and native IDs, verified file/directory counts, held classes and `complete`. Normal admission requires complete independent proof. Original mutable database bytes are not required to keep matching the frozen snapshot SHA after normal writes.
