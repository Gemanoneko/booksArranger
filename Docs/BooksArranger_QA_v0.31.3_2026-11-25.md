## 4. Findings

### Blocker

**B1. Quit does not stop the clean-up between books; it waits for all of them.**
- Repro (desktop entry, the route the shell's tray Quit and `--quit` end in): lane of 10 held books, 8 s stub per book, clean-up running. Send `POST /api/desktop/quit` at `2 of 10` (book 4 in hand). Status answers `phase finishing`, then `parking`, with `waiting_for: [{kind: "critical", title: "a file rename"}]` the whole time. After the request the remaining 8 books were removed one by one, 8 s apart (removal log). The engine was gone **64.7 s** after the request, when the tenth book was done. Plain shutdown route, 14 books, 20 s stub, request at 5 of 14: the engine answered `closing: true` and kept removing; it was gone 181 s later, all 14 done.
- Why it matters: the design is "the book in hand finishes, nothing new starts" (the desktop Quit's own words, and Judy's "A quit mid-run: next launch shows the same total and done count"). Here a book starts after the Quit. On Sergei's catalog that is 115 books, about 40 minutes of NAS work, beginning at launch (m2). A tray Quit, `--quit`, or a Windows sign-out (the safe stop waits for the same critical section) in that window waits for the whole clean-up. This is the "I can't exit" case of 0.30.0 again.
- What I saw in the code (my reading, Ender to confirm): the pass loop over begun writes (`_pass` in `series_backfill.py`, the same shape in `name_write.py`) calls `_finish_active` for each row with no check of `self.stop`; the stop is checked only in the look-up loop and inside the write. `merge_service._close_lookups` waits only the read bound for these daemon threads, but the file-change wait (`critical_sections`) keeps opening again with the next book.
- Not changed by anything I did; it also cannot be seen with a fast local removal (my real-shell lane finished its few books in under a second, and its Quit took 2 s).

### Minor

- **m1. Series books finished by the clean-up read `The rename or move did not finish.`, and I could not see them move.** In the main lane the 9 finished series books stayed in `Alpha Writer\Fixture Saga - N - … .m4b` (renamed, not in the `Fixture Saga` folder) for 47 minutes; their "Could not be renamed or moved" entries kept reading `The rename or move did not finish.` (the rules' next try is an hour away: `SPACING 3600`). A control lane where the writes completed normally (no 0.31.2 hold, no retry) also did not move them in 5 minutes, so I cannot say 0.31.3 caused it. Judy's "if it outlasts the move by more than a minute, report it": there was no move to outlast. Needs Ender's eye on whether the follow-up runs in the real engine.
- **m2. The clean-up starts as soon as anything reads `/api/state`, not after about 2 minutes.** `SeriesBackfill.summary()` wakes the pass when nothing has been counted yet (`series_backfill.py`, the `self.wake.set()` after "unvisited"). Measured: no state read, first removal at +121 s (START_DELAY 120); a page open, first row 1 to 5 s after launch (two lanes) and, in the main lane, exactly when my first page read arrived (+93 s). The shell's hidden window reads state at once, so Sergei's clean-up will start within seconds of launch, alongside the published check that START_DELAY was meant to let finish first. The Brief and Judy's section 2 ("about 2 minutes", "for about 2 minutes nothing shows") do not describe that. The names pass is not woken (125 s), which is the cause of m8.
- **m3. At `0 of N books` the bar is the striped indeterminate style, not empty.** `updateActivity` writes `bar.value` only when it differs from the element's current value; 0 equals the default, so no `value` attribute is ever set and Chromium draws the indeterminate bar until the first book settles (about 20 s on the NAS). Same code for every determinate row, so not new; Judy's check 1 says "empty bar".
- **m4. A new file that is gone before the retry starts reads as engine speech with the old prefix.** Book whose new file was deleted: ledger and log `Series recovery could not verify the files; remaining copies kept: Cannot protect exact file: [WinError 2] The system cannot find the file specified.` Spec 5.3 leaves raw operating-system errors with their prefix ("not specced"), but Judy's check 4 lists "new file deleted (3)" expecting `The new file changed or is missing; the old file is kept.` Row 3 itself I could not produce (section 6), so the check's expectation and the build disagree for the one case that is reachable. Both files were kept; the page does not print it.
- **m5. A held book whose old file is already gone finishes as "removed", and counts in "removed" and "freed".** Old file deleted by hand before the retry: state `done`, counted in `15 old files removed, 272 KB freed` although the app removed nothing. By the code this is on purpose (the retried books all carry `removal_intended`, so a missing old file is taken as removed; N7 `The old file is missing, and the app did not remove it.` needs no intent), but Judy's check 4 expects N7 for it and the done line over-claims by one file in that case.
- **m6. After the library scan ends the Waiting item keeps saying "Waiting for the library scan to finish." for up to a minute.** Measured 25 s (scan ended at +50.8 s, row back at +75.8 s); meanwhile the first part of the line reads `Continues by itself`. The spec says the item is replaced by the row "in the same update"; the retry tick is 60 s.
- **m7. At 360 px the Running region is 6 px too narrow for the step line (46 px at 320).** `#jobs-rows` `scrollWidth` 293 against `clientWidth` 287 (247 at 320); the step line (`white-space: nowrap`, `width 421 px` for the conversion row, 293 px for this row) does not shrink, and the list (`overflow: auto`) can scroll sideways. Nothing overlaps and the document has no horizontal scroll; at 360 px the screenshot shows the text complete, the queue row's longer step cut. Judy's check 12 says "no horizontal scroll"; the CSS is shared by every row.
- **m8. The row's total grows once, and the bar steps back.** The series pass queues its books first and the names pass 5 s to 35 s later (125 s start, or at the first state read for the series pass): main lane `6 of 14` (bar 42 %) became `7 of 21` (33 %) once; the spec says the total "never grows during the run". On Sergei's catalog: `k of 82` then `k of 115`, about two minutes after the start if the state is read at once (m2).
