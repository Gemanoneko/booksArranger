## Findings

**Major — early durable stages do not bind the owned temporary artifact or final no-replace intent.** `transition` validates final/removal proofs but accepts `proof=None` at `copy_intent`, `copied`, `temporary_verified` and `final_publish_intent`; test helper `next` deliberately takes that route. `_history` likewise does not validate those stages. At `final_published`, `_final_proof` accepts a self-consistent `final_publication.published=True` claim without binding it to the exact previously created/verified temporary artifact or a no-replace final publication intent. Consequently the ledger cannot provide the crash-recovery ownership/provenance promised in protocol stages38–41. An engine using only these events cannot distinguish its interrupted temporary/final publication from an unrelated same-name file.

Required correction: define structural stage proofs naming the owned temporary path/root/ancestry and creation intent; bind the completed/verified temporary native identity, full bytes/media proof and generation; require final publish intent to name that same artifact, exact destination and no-replace action; and link final proof to that intent and published native identity. Validate the chain both on transition and `_history`. The native owner still establishes the truth of each claim; the pure ledger should refuse absent/inconsistent claims. Add negative tests for missing proof, changed temporary identity/hash/path, overwritten final intent and altered history. This is not a claim that this pure module currently deletes anything; it has no filesystem side effects. Do not activate migration recovery using the incomplete contract.

**Major — publication eligibility state is unchecked.** `_job` validates durable manifest/output/journal hashes but never checks the durable job's state/stage. The synthetic table omits state entirely, demonstrating that the component can plan a base/replacement binding without proof that its job reached a completed publication state. A needs-attention or unfinished job retaining an output receipt therefore passes the same structural enrollment route. Define and enforce eligible durable states, including any explicitly supported historical replacement disposition, and test refusal of pending/running/publishing/attention states. Physical/native/media eligibility remains a separate mandatory owner preflight; state alone is not sufficient.

Both findings sent directly to primary Ender and Jane. No Critical or always-blocking safety-floor violation identified in the presently inert pure-SQL component. This is not acceptance of its future native integration or a RELEASE CLEAR verdict.

## Contracts that hold in the inspected source

Publication UUID includes job lineage, publication kind and canonical receipt digest, so base/Chapters/Chaptersv2 can coexist. Base/replacement original receipts are compared with durable output and publication intent; frozen manifest/candidate binding and immutable accepted plan digest are retained. Relocation and event writes share savepoints, transitions use generation CAS, append-only triggers refuse event edits/deletion, and history validates stage/generation continuity and stored final proofs. Original location remains effective before location commit; committed stages require final proof and do not fall back to old paths. Malformed/inconsistent bindings fail closed. Native callback acceptance requires literal `True`, not truthiness; after callback, the same row and durable job provenance are re-read. Returned objects are deep copies and unverified envelopes remain explicitly `verified=False`.

Final media/hash/native proof validation is structural, not an actual media check. A callback can supply truth or falsehood; the current module correctly does not claim to perform native verification itself. A caller cannot treat a stored structural proof or unverified envelope as permission to remove source/recovery data.

## Integration obligations not certified here

- Chapter receipts are supplied by the caller: `_job` deliberately does not verify an authoritative repair journal, and `repair_journal_sha256` is optional. Every derived-publication caller must validate its immutable parent/repair lineage and hold the authoritative journal proof. This API by itself does not authenticate an arbitrary chapter receipt. If callers cannot reliably meet that contract, require the journal digest/proof at the component boundary.
- `plan`/`transition` use SAVEPOINT/RELEASE. With no enclosing transaction, RELEASE commits that savepoint transaction. Location commit plus verification-cache invalidation must therefore occur inside an explicit caller transaction; the module does not acquire the operation lease. Native destructive consumers must retain/revalidate the same generation and operation lease through disposal. A callback's postcheck is not a lease extending beyond return, and a SQLite read snapshot cannot establish absence of later external changes after it is released.
- Existing-table validation compares column names, not full SQL constraints/trigger definitions. Treat initialize's check as ordinary version/schema detection, not an audit that a corrupted catalog has genuine PK/FK/append-only constraints. Native activation must not infer broader catalog integrity from it.
- Missing/changed final file is detected only by a supplied native verifier. All completion/current-publication/cleanup/recovery consumers must use the correct verification level and typed refusal. The component does not establish collision checks, cooperative drain, native producer closure, copy/flush/no-replace correctness or deletion authority.
