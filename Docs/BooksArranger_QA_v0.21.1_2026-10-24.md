### F-1 - Minor - focus drops to the top of the page after Esc, Cancel or a keyboard Confirm if the dialog stays open more than about 2 s (opened from the list row)
**Repro** (packaged engine + headless Chrome, trusted input; `ba-0.21.1h-futaba-ui-focus-run1.log`): Output needs attention; focus the Convert… button on the Сказка row; Enter; wait 3 s; Esc (or Cancel, or reach Confirm by keyboard and press it).
**Seen:** `document.activeElement` is the page body. The list is re-rendered by each refresh, so the button the dialog saved to return to is detached (checked: the opener is disconnected at +2 s and is never the element in the row again). Esc pressed at once works, which is why the frozen test passes. Opened from the details panel's Convert… button, focus returns correctly (that button is permanent). After a keyboard Confirm that is accepted, focus also lands on the body, where the spec says it moves to the row's next button.
**Spec:** Judy's section 2 (Esc closes and focus returns; accepted press moves focus on). **Effect:** a keyboard or screen-reader user loses their place in the list after every cancel; a mouse user is not affected. The discard and recovery dialogs save their opener the same way (not tested here). **Status:** open. UI-shaped (Judy), fix by Ender: return focus by the row's key after the render, not by a saved element.

### F-2 - Minor - the dialog jumps 15 px when "Tick both statements first." appears
**Repro:** open the dialog at 1440 x 900, tick one box, click Confirm and convert. **Seen:** Confirm's top moves from y 540.25 to 525 (the status line has height 0 until it has text, and the modal is vertically centered, so the whole dialog shifts up by half the line). The spec says the line "sits below the buttons so nothing moves under the pointer". The pointer stayed on the 40.5 px button in my click, but a click near its lower edge would end below it. **Status:** open; reserve the line's height. UI-shaped (Judy).

### F-3 - Minor - after a refused removal the book has no way out and the panel says something untrue (the handoff's known item, section 4, now with its user-visible face)
**Repro:** fixture C (the driver's `skazka-fence` unknown-file case, served in the real UI): a stray file appears in the old folder after the check; Confirm and convert. **Seen:** the new conversion is published, but the book is in none of Output needs attention, Audiobook Ready or queued ("0 converted out of 1 approved"). The only traces are a text block in the Audiobook jobs panel ("Removing originals - On hold - Old working files of the interrupted attempt were kept, so the original is kept too: An unknown file is in the old working folder; kept") and, under All candidates, "Needs attention - Audiobook job already exists; inspect its current status". The details panel says "These files are not verified for reuse or deletion. Retry uses the original sources... They are deleted once the new conversion is verified." The conversion is verified and they are not being deleted. I then deleted the stray file by hand and restarted the engine: nothing retried the removal in 60 s (`ba-0.21.1h-futaba-c-wait-run1.log`); the original and the old files stay. No button offers anything. **Effect:** nothing is lost (original, old files and the new book all exist), but the book can never finish by itself. Reaching it needs a file to appear in the old folder in the instant after the child's write-deny lease ends, so I rate it rare. **Status:** open, disclosed by Ender; UX-shaped (Judy: copy and an exit), plus a retry for Ender.

### F-4 - Minor - Confirm and convert pressed after the engine went away closes the dialog and does nothing visible
**Repro** (`ba-0.21.1h-futaba-ui-D-offline-run1.log`): open the dialog and tick both boxes; stop the engine; wait 4 s; click Confirm and convert. **Seen:** the dialog closes, no POST is attempted, the row reads K0 again, and the only sign is the page banner "Local server unavailable." The spec's R3b text ("Conversion status unknown") never appears because the app already knows the server is gone and drops the press silently. Before the dialog is opened the app does the right thing: Convert… and Retry are disabled with the tooltip "Local server unavailable." **Status:** open; small race, UI-shaped (Judy: message, or keep Confirm inert while offline).

### F-5 - Minor - the Audiobook jobs banner stays "Needs attention" after both books finished fine (baseline on 6f88e700 not established)
**Repro:** fixture A, press Iron's Retry and Сказка's Confirm and convert; both finish. **Seen:** "2 converted out of 2 approved books - Needs attention - 0 queued - 0 output issues". `state-detail` (`ba-0.21.1h-futaba-probe-state-detail-c2e51662.log`): the engine counts `failed 1`, the superseded failed parent job (still `needs attention` in the job table, not in the attention list); a plain book through the normal queue reads Completed, failed 0. I could not build a pre-delta separate-child retry on 6f88e700 to compare, so this may be the way every separate-job retry has always read; the code that counts it is not in this delta (`merge_service.py`). Same family as the carried "state does not follow the recovery" items. **Status:** open, unverified baseline; Judy/Sergei to decide whether it matters.

### F-6 - Minor, informational - concurrent Confirm presses each write a confirmation, though only one is accepted
**Repro:** `skazka-double`: four simultaneous calls. **Seen:** one accepted, three refused "A retry request is already saved for this book.", but 4 rows in the origin-fact table (each refused press records first, then fails at admission). Harmless today (the latest row wins; one child, one deletion). In the UI the button is disabled while a press is pending, so it takes two browser tabs or a script. **Status:** open; Senua may want to know.
