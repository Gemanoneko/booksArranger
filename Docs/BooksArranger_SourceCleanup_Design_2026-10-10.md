# Books Arranger — snapshot-backed source removal design

Scope: extend the existing v0.4.4 audiobook workflow so a successfully validated, explicitly selected conversion can remove its original selected audio files from Z: while retaining recoverable, exact originals on C:. This document is design only. No original deletion, move, retagging or new conversion has occurred under this task. User authorization covers guarded post-conversion cleanup; another human permission prompt is not a technical gate. Implementation and the first real removal require the frozen code's independent safety/QA checks.

## Bounded implementation surface

- New `source_cleanup.py`: persistent recovery ownership, per-file removal journal, resume/reconciliation, and guarded technical restore operation.
- `native_io.py`: a narrowly scoped exact-file-handle removal primitive. Existing directory/reparse protections, suspended media-process containment and no-replace publication stay intact. Cleanup cannot use path-only unlink, shell deletion or recursive folder operations.
- `merge_service.py` and `audio_jobs.py`: associate cleanup with a completed output, integrate finite queue/pause/resume and overall progress. Audio publication remains separately recorded before cleanup; cleanup failure must never cause automatic reencoding or erase the valid completed-output record.
- `scanner.py`, `groups.py`, `review_backend.py`: durable intentional retirement and recovery state, catalog discovery exclusions by exact ownership, and completed-book status/inspection independent of physically present retired sources. No false read/missing errors or automatic reconversion after intentional removal.
- `web_server.py` and existing View/frontend status surfaces only as Judy's separately committed minimal UX specifies; native review consumer contracts stay consistent. No new permanent-purge or restore button, arbitrary-path endpoint or blanket cleanup action.
- Targeted tests for cleanup/recovery/retirement, existing media validation and HTTP controls. No unrelated format, metadata provider, folder-layout or quality changes.

## Eligibility and immutable cleanup intent

Accept only an opaque completed audiobook job identity. Derive every path from its authoritative completed manifest, registered output and exact selected sources. Podcasts, ebooks, companion images/text and unselected audio are excluded. Initially allow only the two jobs listed below; do not sweep historical jobs or infer that an Eye of God output should have its originals removed.

The cleanup intent binds its own UUID, actor/provenance, completed job/candidate revision, exact ordered selected source hashes/sizes/ns identities, canonical metadata/evidence and selected cover, original output path/hash/size/profile, and original chapter choice. Require the existing complete validation record: full decoded output sample-duration checks, exact intended selected-source coverage/order, canonical author/title/type2, one verified selected cover, optional chapter names/boundaries and supported encoding profile. A saved explicit chapters-off choice remains honored; it is not silently changed into an on requirement. Unknown external publisher completeness is retained as unknown and alone does not block cleanup. Known missing/mixed/unreadable sources or a changed review block it.

The current completed-job creation guard cannot simply be reused: rebuilding a creation manifest rejects the existing final destination, and physically removed originals would fail the creation source checks. Add a distinct completed-parent cleanup guard. It must compare the authoritative persisted job/output/current review and source selection, not adopt an arbitrary existing M4B or weaken an output check.

Before source removal, protect the output's current parent chain and output file against writes/deletion and stream its full SHA256/size. The bytes must equal the output that passed the complete validation gates. A legitimate subsequent iTunes/tag rewrite still changes that hash and requires review; do not silently waive the mismatch. Holding the same output identity during cleanup ensures the validated replacement cannot disappear or change while originals are removed. Do not repeat the entire decode when exact current bytes already match that validated artifact.

## Persistent C: recovery assets

Recovery root is the app-owned `data/source-recovery/<cleanup UUID>/`, distinct from `data/merge-cache/audio-staging/`. Current verified stage snapshots may supply the bytes, but a cache file is not the durable recovery guarantee. Copy into an exclusive owned recovery file, or promote it only under an equivalently proven ownership/immutability contract. Reject reparse points/alias escapes, existing destination collisions and unsupported boundaries. Before the first removal, persist recovery ownership and exact per-source correspondence, finish all selected recovery copies, flush file contents, and full-hash/size verify them under protected read handles.

Record original filename/path, byte hash, size, exact modified timestamp and relevant attributes with each recovery member. Embedded/private audio metadata is preserved in the byte-identical original MP3 snapshot. Assess unsupported extra filesystem streams/alias layouts; fail closed rather than claim a complete recoverable original when that evidence cannot be preserved. Verify free C: capacity for the complete recovery set before copying; copying/fsync/verification failures leave every original untouched. Do not infer durability merely from a pathname or a completed write. Record Windows/volume identities and the supported flush contract; unsupported storage/flush behavior needs attention.

Recovery files are first-class persistent assets. Register them separately from disposable temporary files and make cleanup/hygiene routines exclude them. No automatic expiry or permanent purge. Removing originals frees their selected bytes on Z: but retains recovery bytes on C:; the UI/report must distinguish those facts. Source folders, covers and unrelated siblings remain.

## Exact native original-file removal

Before any removal, acquire protected original parent chains and exact native file handles with READ plus DELETE access, denying other writers/deleters. Check ordinary-file/reparse status, volume/file identity, current size/ns and full streamed bytes using those held identities. Reject unexpected aliases/hard-link ambiguity, paths outside the configured Audiobooks root, and paths belonging to Podcasts or unselected members. Avoid reopening the held DELETE source by a higher-level API whose share flags conflict; the authoritative final guard must use the protected handle evidence and DB identities.

Persist a per-file removal intent before mutation. Hold the validated output and verified recovery member; recheck current DB review/source-set/cleanup revision under the shared review boundary and a short final SQLite transaction. Delete only the exact verified original handle via the supported Windows disposition operation, then close it and verify the expected name is absent. Never remove a swapped pathname, follow an alias, overwrite a replacement, or recursively delete a source directory. Pause completes the current atomic disposition/catalog checkpoint then stops between files. Long hashing/copying remains outside the short DB publication gate; no multi-minute database lock.

The mapped-Z disposition and required source-sharing behavior need a bounded disposable owned fixture with a positive control, tested after the implementation is pinned. Existing rename support does not establish this new delete primitive's behavior. Any unsupported operation, permission/share conflict or unexpected delayed removal stops with accurate recovery state. Do not fall back to a weaker path deletion.

## Partial cleanup, restart and restoration

Persist intent and each member's state (`backup verified`, `removal intended`, `removed`, `restored`, or `needs attention`) independently. A crash after disposition but before catalog commit is reconciled from the owned intent, exact recovery/output hashes and source-name state; no arbitrary missing file is treated as proof of successful removal. If an original path still exists, verify its current identity/hash before continuing; a different replacement is preserved and flagged. Never repeat encoding to recover cleanup.

On restart, reconcile journaled states and show saved cleanup progress. Resume continues the remaining exact members under fresh output/review/recovery/source checks; stopped/failed members remain untouched. If review, output, recovery or source identity changes, hold cleanup and keep the valid output plus all still-present originals and recovery assets. A partial cleanup reports the exact moved/remaining counts, rather than claiming all originals retained or all removed.

Guarded restoration is available through a bounded technical job-ID route/helper without a new UI control in this milestone. It revalidates the recovery store and exact correspondence, copies immutable original bytes into an exclusive owned destination-side temporary under the original source-root/parent protections, restores supported source timestamps/attributes, and uses the existing exact-handle no-replace publication. Existing files at the original names are preserved; a collision or unknown ownership needs attention. Journal each restoration and update retirement provenance only after verified publication. The completed audiobook remains available and is never overwritten. No permanent purge is part of this design.

## Catalog and review continuity

Use dedicated cleanup/recovery/member tables and intentional retirement records rather than overloading `files.missing`, deleting historical manifest data or setting a read error. Exact retired originals are excluded from active scan queue/group membership; exact owned recovery assets never become book candidates. Ordinary new files are still discovered, and unrelated same-folder files remain visible. A reappearing original-name file is checked as a new/changed object and must not be blindly skipped because an old retirement record exists.

Completed book records retain their identity, metadata evidence, original ordered source list, output and removal/recovery facts. Status/page filters operate over the entire library before pagination, with output availability and cleanup failures reported distinctly. Scan completion must not replace an intentional retirement with a false missing-source error or offer automatic conversion of that old source group. Historical sources remain inspectable as provenance; current output inspection is the actual validated artifact. Restore reactivates only the corresponding verified source records and cannot overwrite current unrelated reviews.

Overall finite queue semantics: conversion/output publication first, then guarded cleanup. Pause/Resume and shutdown cover the cleanup worker as well as encoder work; a cleanup failure is separately persisted and never represented as an audio encode failure requiring reconversion. Existing pending/failed jobs cannot clean sources. Newly created explicitly selected jobs may queue cleanup under the user-authorized workflow, but no library-wide cleanup is inferred from merely opening the app.
