# Books Arranger — 24-hour recovery retention extension

Date: 2026-10-10. Status: design only; implementation waits for the concurrent v0.7.0 owner to hand off. This extends existing guarded storage cleanup, rather than replacing its file-disposition mechanisms. Sergei selected one day: exactly 24 elapsed hours after successful removal of the selected original tracks. Automatic checks run at app startup and periodically while it runs. Manual deletion applies to the selected completed audiobook's recovery set only.

## Current baseline and actual storage

The published v0.6.0 `StorageCleanup.run` currently removes registered staging and recovery files together immediately after successful source cleanup. There is no retention timer, startup scheduler or manual recovery-delete HTTP/UI control. The concurrent v0.7.0 work adds progress and guarded empty source-folder housekeeping; its changes must be preserved.

A read-only SQLite inspection and exact registered-path existence checks found MirrorMask's 11 recovery receipts (114,906,562 bytes), Snapshot's 10 (243,387,177 bytes), and another completed job's 67 (575,583,339 bytes) already marked `removed`, with zero registered recovery files still present for each. Empty UUID directories remain. This extension cannot recreate previously discarded copies and must show them as unavailable, never fabricate a new retention interval for absent files.

## Backend ownership and boundaries

Split working-file cleanup from recovery deletion in `storage_cleanup.py`: verified staging artifacts can still be removed after successful conversion/source cleanup; recovery files remain until expiry or explicit per-book deletion. Existing `storage_cleanup_files` exact file facts, hash/size, single-stream and hard-link checks, protected output handles, ancestor protections and native disposition journal remain the deletion mechanism. Do not add recursive path deletion or unregistered file discovery/deletion. Unknown content and replacement names remain untouched.

Add durable recovery-retention records keyed by source-cleanup UUID and completed audio job, containing policy version, immutable successful-source-removal UTC timestamp, expiry UTC timestamp, binding to manifest/output hash, and separate deletion state/reason/updated fields. Capture completion time in the same transaction that commits successful source cleanup. Do not derive age from backup file modification times, mutable poll/status timestamps or timer activation. For an existing completed recovery set, migrate only a trusted existing terminal completion timestamp supported by its durable completed cleanup receipt; malformed or uncertain evidence preserves files and reports attention. Previously purged sets remain purged. Exactly 86,400 elapsed seconds is eligible, never earlier; backward wall-clock movement defers deletion. Restart reuses saved deadlines, never resets them.

Keep `storage_cleanup_jobs` working-artifact success independent from recovery retention/deletion, so a book remains converted while its recovery set is intentionally retained. Preserve source retirement/catalog rows and output success when recovery copies expire. Update `source_cleanup.py` status and restore admission to use the separately confirmed recovery state and actual remaining registered files. Restoration remains unavailable once purge has started; active restoration and purge are mutually exclusive under the shared operation admission lock.

Reuse guarded source-retirement validation, including exact manifest members and durable original-removal receipts. Integrate v0.7.0's exact removed-directory ancestry receipts when source parents no longer exist; do not weaken absence checks or accept arbitrary missing parents. Recheck unchanged validated M4B output and complete terminal source cleanup before recovery disposition. Preserve copies for incomplete, uncertain, paused or failed cleanup, restoration, invalid output, scan/conversion activity, changed identity/hash, unknown content and unsupported native operations.

## Service and HTTP contract

`merge_service.py` owns one bounded background retention worker and shared admission with scans, conversion, source cleanup, restoration and manual purge. Startup schedules a check after service construction; periodic checks use an interruptible event wait, stop when closing, and process only eligible recorded jobs. No startup historical source enrollment, new conversion or library scan is permitted. Busy work defers expiry until a later check. On shutdown, stop and join the owned worker before database/catalog ownership is released.

Expose per-book recovery status in existing state/inspect responses: confirmed remaining count/bytes/location, immutable expiry, eligibility, state and reason. Polling reads status without hashing audio or deleting files. Unknown counts are not represented as zero. A GET never mutates purge state. Add a guarded same-origin/token-protected POST endpoint accepting only job UUID plus an observed bounded recovery-set revision/token, never a client pathname or arbitrary timestamp. Admission rejects stale confirmation, busy scan/queue/cleanup/restore, uncertain recovery set or closing server. Recheck all deletion guards in the worker; manual deletion does not bypass them. Preserve existing HTTP error conventions.

The manual confirmation binds the selected set, count and bytes. A successful response may start asynchronous deletion; UI reports progress and only says removed after durable terminal confirmation. Double requests serialize/idempotently resolve to the same set; retries and process restart reconcile journaled native disposition. Partial purge reports actual remaining files and blocked restoration, never promises a complete backup. Distinguish unknown absence from a native-disposition-confirmed absence according to the existing journal semantics.
