# Books Arranger shared-root relocation — early design review

Status: advisory design review, 2026-11-13. This is not release clearance. Reviewed the existing 0.27.0 contracts and the proposed opt-in relocation envelope; no implementation or release commit is certified. No suite, build, live catalog operation, app launch, migration or filesystem mutation outside this report was performed by the reviewer.

## Reviewed proposal

An offline source phase and target seal produce an immutable descriptor binding an exact catalog, generation, old/new roots, directory identities, file facts and full hashes. A per-installation descriptor path and SHA-256 opt in. Historical receipts remain unchanged. Runtime permits only the approved junction, holds its native entry and ordinary physical target, and uses explicit historical comparison helpers. Actual native facts remain actual. Existing installations without the opt-in retain strict behavior.

The reported native baseline demonstrations were performed by Ender, not repeated here: real junction catalog admission fails; real copied pending and completed artifacts fail old identity receipts and pass with actual target facts. Those are evidence of the problem, not acceptance of this design.

## Required safeguards and open design issues

1. **Fence both catalogs and the old writer path.** `catalog_owner.py:24` locks the selected catalog's `.lock` pathname; copies have independent native locks. `migration_operation.py:35` retains one database identity but intentionally permits SQLite writes. Acquiring the target lock does not establish that the source is frozen. Define source drain, source/target ownership, publication/activation states, and durable prevention of an old 0.27 process reopening the original writable source after activation. Keep this fencing through seal and switch. Rollback must fence both copies and reconcile post-switch writes before restoring authority.

2. **Bind activation to a catalog generation, not a reusable JSON file.** The initial source database digest can establish copy provenance, but normal startup subsequently changes database bytes. Define the one-time activation transaction, its catalog-native identity lease, a persistent generation record, replay rules and behavior on disagreement between descriptor/config/catalog. A descriptor SHA pins bytes; it does not itself prove operator provenance or a current owner. Tampered, stale, duplicated, interrupted and wrong-catalog envelopes must refuse before the backend or maintenance begins.

3. **Do not convert a copy into producer-closure authority.** `producer_recovery.py:171` binds origin evidence to scope, machine and the complete native record; `producer_recovery.py:345` protects retained native state; `producer_recovery.py:365` validates hashes of saved proof; `producer_recovery.py:370` and the following boot checks preserve locality/closure evidence. Keep the original proof chain exact. A separate location binding can establish where already-proven bytes now live; it must not invent the old producer's closure, local origin, later boot or right to discard retained work. A copied unresolved producer remains unresolved unless its existing independent recovery contract is satisfied.

4. **Comparison helpers need operation context.** `facts_match(path, actual, expected)` must be catalog/generation scoped and consult only the exact approved historical entry. An ancestry helper must also take the operation path and catalog/generation, not just two tuples. Preserve path containment, exact expected receipt, stream/link/attribute constraints and same-handle hashing. Equality of current facts remains the ordinary fast path; only old historical expected facts may translate. Runtime comparisons between newly opened handles, pre/post rename facts or a just-created producer's identities must remain strict.

5. **Hold and revalidate both paths through the destructive operation.** `native_io.py:93` currently protects every directory ancestor; `native_io.py:142` revalidates native identities. An allowed mount-point entry needs exact tag/substitute-target validation through the held reparse handle, bounded parsing and a proven deny-write/delete sharing fence. The physical target's complete ordinary ancestry needs its own held fence. Retargeting or replacement must fail while these handles are held. Validation only at descriptor load or before opening the file is insufficient. Unrelated reparse ancestors/descendants, other projects and unmapped library paths stay rejected.

6. **Keep current media/receipt checks and transaction leases.** `working_lifecycle.py:492` and `working_lifecycle.py:739` compare complete native facts and full content. `storage_cleanup.py:220` protects publication identity/ancestry/content; `storage_cleanup.py:237` rechecks publication generations inside the disposal transaction. The new location binding is an additional fact source, not permission to skip those controls. Its generation/descriptor lease must survive through the final disposition and catalog compare-and-set. A change between successful verification and deletion must refuse.

7. **Cover more than the main catalog and working-files table.** `openlibrary_index.py:165` checks a producer receipt for both index database and persistent journal; `openlibrary_index.py:191` and `openlibrary_index.py:195` check them on read. Preserve those immutable owner receipt bytes and bridge each exact physical leaf separately. Audit existing repair journals, recovery backup facts, source-cleanup records, retained producer records and publication-location envelopes explicitly. A consumer inventory should classify each comparison as current-runtime, historical file, historical ancestry, whole proof, or unrelated/unmoved. Unknown formats must produce a visible held obligation rather than receive generic recursive translation.

8. **Load the exact pin in every executable path.** `desktop/main.js:194` uses the backend's restricted environment; `desktop/main.js:604` launches read-only tools differently, and `desktop/main.js:632` starts the update lease. All catalog inspection, startup guards, legacy/CLI entry points and migration tools need the same explicit scoped configuration before their first native guard. Processes without an explicit relocation must retain legacy behavior. Installing/upgrading/restarting must not lose the pin or silently initialize a second catalog.

9. **A file census is not a writer fence.** Source hashes, directory membership, facts, ADS policy and sidecar set must be collected at a stable ownership point and rechecked before sealing. Unknown files, changed bytes with restored size/time, hardlinks, reparse descendants, unexpected SQLite sidecars, incomplete producer capture and disappearing files must not be adopted by name. Define what remains held when one class is unsupported, and do not label the complete migration ready until required resumable obligations are supported.

## Minimum private acceptance cases

- Ordinary current installation and second-PC no-opt-in behavior still work; no I-drive requirement appears globally.
- Actual C-to-I copies and a real junction exercise startup, pending/attention attempt handling, completed cleanup, recovery backup use, retained producer protection, repair and index owner receipts. Include a representative real conversion and restart/resume.
- A different catalog, descriptor generation, alias target, file ID, parent ID, receipt, byte hash, stream/link shape or schema refuses. Keep an ordinary good control for each failure detector.
- A second process cannot write/retarget/delete the alias, target ancestry, descriptor or exact protected artifact during verification/disposition. Prove the Windows sharing behavior with real competing handles.
- Interrupt source preparation, target sealing, activation, first restart and cleanup intent at durable boundaries. Retrying is idempotent, original receipts remain byte-identical, and no phase grants ownership or successful removal solely from a missing filename.
- An unavailable I drive or missing pin refuses without a C/personal-folder fallback. Newly written records contain actual target identities and remain usable after restart; old bindings cannot authorize an unrelated newly created file at the same name.
- Fence both copies for rollback; demonstrate refusal of a stale rollback after new decisions/jobs/publications or source retirement until those writes are reconciled.

## Installer and uninstall addendum

The parent subsequently reported Sergei's explicit request for normal versus complete cleanup of app-owned old locations, plus installer discovery/browse of an existing catalog or an explicit new catalog. This addendum addresses that requested design only; no installer implementation was reviewed. Current `package.json:63` disables the directory chooser and `package.json:67` retains app data on uninstall.

- **An old pathname is not an old copy.** After the shared-root move, C: and I: may name the same active object. Before cleanup, resolve native identity under held ordinary/approved-alias boundaries and compare with every active catalog/profile/work root. Deduplicate aliases. Never delete an active I: target through its C: junction, remove the shared junction, or recurse across a link because a lexical path looks like a former location.
- **Normal uninstall remains retaining.** Complete cleanup needs an explicit, bounded preview of app-owned targets and exclusions, then positive ownership/provenance and full process/handle closure. A folder name, old registry value, age, absence of an encoder, or containment in the development checkout is insufficient authority. Preserve libraries, Git/source/worktrees, unrelated siblings, retained recovery obligations and any other installation's active data. A migration backup needed for rollback is retained unless separately and explicitly selected with its consequence understood.
- **Discover safely, then choose deliberately.** Prefer known app settings/install locations and user-selected folders over an unbounded drive/NAS crawl. Discovery must not initialize or migrate a schema, checkpoint, delete a lock, copy the main DB alone, or start workers. `desktop_catalog.py:36` deliberately observes a present WAL rather than using immutable mode and ignoring committed WAL state. Reuse the supported recognition/schema/integrity rules and distinguish unavailable/busy/corrupt/unsupported catalogs from absence. Do not claim zero filesystem writes from a read-only SQLite connection without accounting for shared-memory handling.
- **Selection does not transfer authority.** Deduplicate the same discovered catalog through aliases by native identity. A selected catalog needs its actual physical/logical location, relocation generation, version compatibility and existing owner checked again at launch. An existing writer is a refusal or supported handover, never permission to reset history. Browse cancellation preserves the previous choice. Starting anew is a separate explicit empty-target operation and never overwrites or silently substitutes for an unavailable existing catalog (`desktop_catalog.py:15` onward).
- **Retest uninstall and upgrade against aliases.** Private acceptance must cover active old/new owners, C→I aliasing, renamed rollback originals, failed/partial upgrade, two installations, missing I:, canceled selection and unsupported schema. A deliberately unsafe old-path deletion target must be observed to refuse; a separate exact disposable app-owned target supplies the positive complete-cleanup control. Check actual files and retained native identities afterward, not just installer exit codes.
