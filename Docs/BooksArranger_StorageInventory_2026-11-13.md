## Load-bearing finding

Windows reports Z: as DriveType **4 (network)**, mapping `\\NAS3247BD\Public`; it advertises FileSystem `NTFS`, VolumeName `Public`. Its network-drive classification governs here: the string NTFS is not evidence that SQLite sees a local filesystem. Observed capacity 3,838,581,809,152 bytes, free 397,381,943,296 bytes at inspection. No NAS manufacturer, model, operating system, CPU architecture, container/VM feature, administration access or physical local server path has been established. The hostname is not a reliable model identifier.

SQLite explicitly states WAL does not work over a network filesystem: [Write-Ahead Logging](https://sqlite.org/wal.html). The current application unconditionally ensures `PRAGMA journal_mode=WAL` in `scanner.connect`. Changing to rollback journals does not establish safe SMB locking/durability or solve the application's Windows process/file-identity requirements. Do not apply that shortcut or a VHD workaround without a separate architecture decision.

SQLite's supported architectural direction is to colocate its engine with its database and cross the network using an application protocol: [SQLite over a network](https://sqlite.org/useovernet.html). This means a NAS-local service using a native NAS filesystem path, **not** a container that opens the Windows SMB mapping.

## Shared-folder junction is not sufficient for Books Arranger

Existing production guards intentionally reject reparse ancestors. In native_io.py DirectoryBoundary.__enter__, each opened ancestor's attributes are checked for FILE_ATTRIBUTE_REPARSE_POINT and refused. Its ordinary() normalizer uses abspath rather than resolving arbitrary junctions. Build/native helpers similarly retain ordinary ancestry. Therefore C:\Antigravity Projects becoming a junction is not transparent to this application: a configured C: database/work path can fail safe even while ordinary file reads work.

Furthermore, copying from C: to I: changes the volume/file identities stored in producer, working-artifact, cleanup and other receipts. Matching names/content or redirecting dataDir is insufficient to authorize deletion, reuse or resumption. Changing all path strings, following arbitrary reparse points or relaxing identity checks would weaken the existing safety model and is not an approved fix.

No supported no-code migration of all current resumable work has been established. A safe move requires a concrete reviewed location/generation binding or other verified supported reconciliation for copied catalog/work/recovery artifacts, preserving immutable historical manifests. Existing publication relocation code is relevant precedent, not proof it covers all application-state relocation. If this cannot be prepared within the shared-folder work, exclude/preserve Books live state and explicitly hold its relocation rather than claiming it ready.

## What staging cleanup actually does

The observed 14.09 GiB is **not** a disposable idle cache classification. The application already cleans eligible work under explicit recorded proof:

- Successful completion calls MergeService._after_completed/_prune_completed and _prune_working; StorageCleanup verifies the published audiobook, output binding, exact working artifacts and ownership before disposition. Cleanup failure does not erase conversion success and is journaled for attention.
- start_retention normally wakes every 60 seconds (2 seconds for queued explicit recovery deletion). It invokes working.reconcile(limit=1, storage=...) for closed/published attempts only and idle admitted recovery/temporary/folder maintenance. Attention/source-retained attempts require relevant explicit admission rather than every idle tick. A busy scan/conversion/operation, closing or update hold can defer maintenance. This is not recursive age-based deletion.
- WorkingLifecycle requires durable producer closure and recorded native file identities/bytes. Unknown/unrecorded members, unclosed producers, isolated retained attempts, source snapshots needed because originals/artwork are unavailable, uncertain diagnostics, published-held obligations and changed receipts remain. An encoder process ending alone proves none of these conditions.
- Retry/Repair/Clear working files use the same per-job verified disposal/admission contracts. Transient sharing/access/unreachable failures have classified retries (normally 60 seconds); permanent identity/provenance failures preserve files for explicit review. Recovery source copies are purged only after full output verification and valid cleanup authority, not merely after time passes.
